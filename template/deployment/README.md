# Kubernetes deployment

This directory contains the Kubernetes manifests for the application workload.

## Deployment model

This repository follows GitOps.
`.github/workflows/release.yaml` builds and pushes the image, and updates `deployment/k8s/deployment.yaml` with an immutable image tag for Argo CD to reconcile.
Argo CD applies manifests from git.

## Sealed Secrets

Runtime secrets are managed as SealedSecrets in `deployment/k8s/`, they need to be created or refreshed on changes using `.github/workflows/refresh-sealed-secrets.yaml`.

Resulting committed files:

- `deployment/k8s/app-env.sealedsecret.yaml` for the application secrets
- `deployment/k8s/ghcr-secret.sealedsecret.yaml` for Argo to pull the image published in the release workflow

Generating secrets requires the public cert generated by `kubeseal` on the cluster set as Github Variable `SEALED_SECRETS_CERT`.

The public cert can be fetched like this:

```bash
kubeseal --fetch-cert \
  --controller-name sealed-secrets-controller \
  --controller-namespace kube-system \
  > sealed-secrets.pem
```

## GitHub Actions configuration

Create these repository variables under **Settings > Secrets and variables >
Actions > Variables**:

| Variable                 | Purpose                                                                           | Example                          |
| ------------------------ | --------------------------------------------------------------------------------- | -------------------------------- |
| `K8S_NAMESPACE`          | Kubernetes namespace for the SealedSecrets                                        | `my-app`                         |
| `APP_ENV_KEYS`           | Space- or comma-separated secret names to include in the application SealedSecret | `DATABASE_URL API_KEY`           |
| `SEALED_SECRETS_CERT`    | Public PEM certificate from the Sealed Secrets controller                         | contents of `sealed-secrets.pem` |
| `DOMAIN_NAME`            | Domain managed by the release workflow                                            | `example.com`                    |
| `HETZNER_S3_NAME`        | Hetzner Object Storage bucket containing Terraform state                          | `terraform-state`                |
| `TF_STATE_KEY`           | Terraform state object key                                                        | `my-app.tfstate`                 |
| `HETZNER_S3_ACCESS_KEY`  | Hetzner Object Storage access key                                                 | access-key id                    |
| `K8S_LOAD_BALANCER_HOST` | Hostname of the Kubernetes ingress load balancer                                  | `ingress.example.com`            |

Create these repository secrets under **Settings > Secrets and variables >
Actions > Secrets**:

| Secret                             | Purpose                                                |
| ---------------------------------- | ------------------------------------------------------ |
| Each name listed in `APP_ENV_KEYS` | Value sealed into `app-env.sealedsecret.yaml`          |
| `GHCR_USER`                        | GitHub Container Registry username for the pull secret |
| `GHCR_TOKEN`                       | GitHub Container Registry token for the pull secret    |
| `HETZNER_S3_SECRET_KEY`            | Hetzner Object Storage secret key for Terraform state  |
| `HETZNER_API_KEY`                  | Hetzner API key used by Terraform to manage DNS        |

The refresh workflow passes the complete GitHub Actions secrets context to the
renderer, but only names listed in `APP_ENV_KEYS` are written to the
application SealedSecret. Keep `APP_ENV_KEYS` limited to the secrets required
by the application. `GHCR_USER` and `GHCR_TOKEN` are also used to generate
`ghcr-secret.sealedsecret.yaml`.

GitHub provides `GITHUB_TOKEN` automatically; it is used to publish the image
and create the refresh pull request. Do not create it manually.
